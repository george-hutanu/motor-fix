# Research: ST-164 admin actions in the audit history

No `NEEDS CLARIFICATION` is left in Technical Context; every decision below is taken from the repository (path:line) or from `spec.md` Clarifications and `context.md`. Retention (T10) and anonymisation stay open with the lawyer and are not design decisions of this plan.

## R1. The live test's entry is one `audit.record` inside its existing transaction

- Decision: `LiveController.test` takes `@CurrentActor() actor: Actor` beside its body and injects `@Inject(AUDIT_PORT) private readonly audit: AuditPort`. Inside the `$transaction` it already runs, after the target is found and before (or after) `events.record`, it calls `this.audit.record(tx, { action: 'create', actorId: actor.accountId, actorRole: actor.role, kind: 'live.test', newValue: body, subjectId: target.id, subjectType: 'account' })`. `EventsModule.register` adds `{ provide: AUDIT_PORT, useClass: AuditService }` to its providers.
- Rationale: the route's whole use case is the controller's transaction (`live.controller.ts:84-98`): target lookup, 404, outbox row. Adding the entry there keeps FR-001's "same transaction" with no new service (Principle I; a `LiveTestService` would be a single-implementation layer). `AuditService` has no constructor dependencies (`audit.service.ts:36`) and every module provides `AUDIT_PORT` for itself: `auth.module.ts:91`, `garages.module.ts:56`, `notifications.module.ts:73`; `AuthModule` does not export it (`auth.module.ts:56-66`), so `EventsModule` needs its own line. The subject is the target account and the new value the validated body `{ accountId }` (spec Clarifications 1 and 5; FR-002). The writer fills `actorName` from the account inside the transaction when none is given (`audit.service.ts:64-73`), so the first name needs no lookup here. A non-admin never reaches the body (`@Requires('admin.users')` in the guard, `live.controller.ts:77-80`), so a 404 writes nothing (FR-001, scenario 7). The service-level coverage spec scans `*.service.ts` only (`audit-coverage.spec.ts:170-181`), which is why this controller was uncovered; the HTTP guard (R3) closes that gap.
- Alternatives: moving the transaction into a new service (a layer with one caller); recording the entry after the transaction (breaks "together or not at all"); subject `live_update` with the fresh `subjectId` (the spec decides the account).
- Evidence: `libs/domain/src/events/live.controller.ts:40-47,77-99`; `libs/domain/src/events/events.module.ts:52-69`; `libs/domain/src/auth/auth.module.ts:56-66,91`; `libs/domain/src/garages/garages.module.ts:56`; `libs/domain/src/notifications/notifications.module.ts:73`; `libs/domain/src/audit/audit.service.ts:36-73`; `libs/domain/src/audit/audit.port.ts:4-23,30-33`; `libs/domain/src/auth/actor.guard.ts:43-46`; `libs/domain/src/audit/audit-coverage.spec.ts:170-181`.

## R2. The test message's entry is written first, in its own transaction, by the use case

- Decision: `NotificationsService.sendTestMessage(actor: Actor, accountIds: readonly string[])`. After the existing recipient check (`notifications.service.ts:167-177`, 400 `unknown_recipient` before anything is written) and before the per-account loop, it runs `await this.prisma.$transaction((tx) => this.audit.record(tx, { action: 'create', actorId: actor.accountId, actorRole: actor.role, kind: 'notification.test', newValue: { accountIds: [...accountIds] }, subjectId: actor.accountId, subjectType: 'account' }))`. `NotificationsController.test` takes `@CurrentActor() actor: Actor` and passes it. The service spec's one existing call (`notifications.service.integration.spec.ts:349`) gains an actor argument.
- Rationale: FR-003 decides the order: the change is a set of queued rows written one account at a time in separate transactions (`notify`, `notifications.service.ts:118-141`), so one transaction holding entry and rows does not exist; the entry commits first, a failed entry queues nothing, and a send that fails afterwards answers 5xx with the entry kept, recording the attempt. The service already injects `AUDIT_PORT` (`notifications.service.ts:20,105`) and is the one use case the controller calls (`notifications.controller.ts:18-21`), so a later caller records the entry too (Principle V). The subject is the calling admin because the message goes to many accounts (spec Clarification 5), and the new value is the validated body `{ accountIds }`. `NotificationsService.notify`, `build` and the delivery methods stay on the coverage spec's excuse list (`audit-coverage.spec.ts:118-137`): a notification's delivery rows are not a change to anyone's data; the admin's act of sending the test is, and this entry records it.
- Alternatives: the entry in the controller (then the MCP server or a script calling the service would miss it); one entry per recipient (the spec decides one per call); wrapping the whole loop in one transaction (changes `notify`'s per-account commit and lock shape for a test tool).
- Evidence: `libs/domain/src/notifications/notifications.service.ts:20,97-106,118-141,166-185`; `libs/domain/src/notifications/notifications.controller.ts:10-22`; `libs/domain/src/notifications/notifications.service.integration.spec.ts:343-351`; `libs/domain/src/audit/audit-coverage.spec.ts:118-137`.

## R3. The guard reads the OpenAPI document and calls every `admin/*` route once as an admin

- Decision: `apps/api/src/admin-audit.integration.spec.ts` boots with `apiBoot()` and lists routes exactly as `admin-routes.integration.spec.ts:56-66` does (`openApiDocument(app).paths` filtered to `/api/v1/admin/`, one `{ method, path }` per method). One seeded admin (`AccountsService.createAccount`, roles `['admin']`, as `:34-43`) signs every call (`signAccessToken`, `:45-46`). A fixture table `FIXTURES: Record<string, (ids: { admin: string }) => object>` keyed `'POST /api/v1/admin/live/test'` etc. gives each changing route its known-good body; a `GET` needs no row and is sent with no body. `it.each(routes)` runs one case per route, titled by `METHOD /path`: `count(admin)` before, the call, `count(admin)` after; expect the status to be 2xx (the failure message carries the status), and for `POST|PUT|PATCH|DELETE` `after - before >= 1`, for `GET` `after === before`. A changing route with no fixture row fails that same case with the route in its title. The `count` is `SELECT count(*) FROM activity_log WHERE actor_id = $1` through the `pg` `Client` the neighbouring spec already opens (`:103-116`), because `@motor-fix/domain` exports neither `PRISMA` nor `AUDIT_PORT` (`libs/domain/src/index.ts`) and one query is smaller than a new export.
- Rationale: FR-004 asks for the API's own route list so a route that forgets the writer fails without the test being edited beyond its table, and for one failure per route naming it; `it.each` gives that for free. Counting the admin's own entries before and after each call (Clarification 3) tolerates the verification approval's two entries and ignores what other specs left in the table. Each route is called once, so the news route's monthly claim (`news_send.month` is the primary key, `notifications.prisma:100-107`) is not hit twice in one run; `beforeAll` deletes `news_send` for the current month first (`DELETE FROM news_send`), as `news.api.integration.spec.ts:86` does with `newsSend.deleteMany()`, so a second run on the same database is not refused with 409. Today's fixtures: live test `{ accountId: admin }` (an admin is an account, `live.controller.ts:85-90`), notifications test `{ accountIds: [admin] }` (`TestMessageDto`, `notifications.dto.ts:12-26`: 1–20 unique uuids of existing accounts), news `{ title: { ro, en }, text: { ro, en } }` (`SendNewsDto`, `notification-preferences.dto.ts:248-289`; zero consenting drivers still answers 202, `news.service.ts:78-90`). A logged-read `GET` (none today) would be marked in the same table by its own story with the expected delta of 1 (Clarification 4); the plan adds no field for it now.
- Alternatives: a hand-kept list of audited routes (misses the next route); a decorator on each audited handler plus a registry (a mechanism nobody else reads, Principle I); asserting on `GET /api/v1/audit-history` instead of the table (slower, and that endpoint's filters are ST-391's, not this test's).
- Evidence: `apps/api/src/admin-routes.integration.spec.ts:1-66,103-116`; `apps/api/src/api-boot.testing.ts:1-80`; `libs/domain/src/index.ts:1-35`; `libs/domain/prisma/schema/notifications.prisma:100-107`; `libs/domain/src/notifications/news.api.integration.spec.ts:84-91`; `libs/domain/src/notifications/news.service.ts:78-116`; `libs/contracts/src/notifications.dto.ts:12-26`; `libs/contracts/src/notification-preferences.dto.ts:248-289`; `libs/contracts/src/live.dto.ts:4-8`.

## R4. The guard and the 404 spec stay two files

- Decision: the guard is a new file, `admin-audit.integration.spec.ts`, not a `describe` inside `admin-routes.integration.spec.ts`.
- Rationale: each file boots the API once (`apiBoot()` takes the database turn and starts a store, `api-boot.testing.ts:13-25`); the 404 spec's cases call every route as four non-admin roles and never change data, while the guard changes data and clears `news_send`. Two files keep each spec's setup its own and let Jest run them in its usual per-file order; the prompt for this phase names "one guard integration spec beside" the existing one.
- Alternatives: one file (one boot saved, two unrelated setups mixed).
- Evidence: `apps/api/src/api-boot.testing.ts:13-25,55-78`; `apps/api/src/admin-routes.integration.spec.ts:16,48-56`.

## R5. Which specs prove which requirement

- Decision: FR-002 in `live.api.integration.spec.ts` (the admin's live test leaves one `activity_log` row: `actorId` admin, `actorRole 'admin'`, `actorName` the first name, `action 'create'`, `subjectType 'account'`, `subjectId` the target, `kind 'live.test'`, `newValue { accountId }`, `viaAssistant false`; the existing 404 cases gain "and writes no entry"). FR-004 in `admin-audit.integration.spec.ts` (R3), including the overview `GET` leaving none (User Story 3). ## R6. No OpenAPI or client change

- Decision: `apps/api/openapi.json` and `libs/data-access` are not regenerated.
- Rationale: the routes, their DTOs and their responses do not change; `@CurrentActor()` is a `createParamDecorator` reading the request (`actor.guard.ts:43-46`), which `@nestjs/swagger` does not document, as the news route shows today (`news.controller.ts:50-55` takes the actor and its OpenAPI entry lists only the body). The entries are read through the existing `GET /api/v1/audit-history` (391-FR-008, `admin_actions` area), unchanged.
- Evidence: `libs/domain/src/auth/actor.guard.ts:43-46`; `libs/domain/src/notifications/news.controller.ts:43-56`; `libs/domain/src/audit/audit-history.controller.ts`.
