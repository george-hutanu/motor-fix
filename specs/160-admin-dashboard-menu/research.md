# Research: ST-160 open the admin dashboard and its menu, admins only

No `NEEDS CLARIFICATION` is left in Technical Context; every decision below is taken from the repository (path:line) or from `context.md`. The open items the clarify session left to the owner (the operations command that grants `admin`; the end-to-end live rise after ST-116) are not design decisions of this plan and stay in `spec.md` Assumptions.

## R1. The overview is one route in the garages module, counted by the verification service

- Decision: `GET /api/v1/admin/overview` is `AdminOverviewController` (`@Controller('admin')`, `@Get('overview')`, `@Requires('admin.garages')`, `@ApiTags('admin')`) in `libs/domain/src/garages/`, registered in `GaragesModule.register` beside the public garages controller. It answers `AdminOverviewDto { garagesWaiting: number }` from a new `VerificationService.countWaiting(db)`: `db.verificationFile.count({ where: { status: { in: ['submitted', 'in_review'] } } })`, read at each call, no cache. `db` is `Prisma.TransactionClient | PrismaClient`; the controller passes the injected `PRISMA` client, a later story (ST-301's four counts) its transaction.
- Rationale: the only counter is a count of verification files, which the verification service owns (its `FROM` table names the same two statuses as "decidable", `verification.service.ts:36-41`); the garages module already wires `VerificationService`, `AUDIT_PORT` and `EVENT_PORT` (`garages.module.ts:33-53`). One controller per admin concern is the repo's shape (`notifications.controller.ts:8-23`, `live.controller.ts:77-99`). The 404 for every non-admin is the guard's, before any body is read (`actor.guard.ts:70-74`, `policy.ts:45-52`): every `admin.*` capability is in the `admin` row alone (`capabilities.ts:44-51`), so FR-002 holds for the four other roles whichever `admin.*` capability a route names. 401 without a token and 403 for a suspended account are the guard's too (`actor.guard.ts:48-52,114-119`); 404's code is `not_found` by the problem filter's table (`libs/contracts/src/problem.ts:40`).
- Alternatives: a count inside the controller with the Prisma client (a rule outside its use case; ST-301 would copy it); an `AdminModule` (a module for one route is a single-implementation layer, Principle I); `@Requires('admin.settings')` (the counter is the garages queue's).
- Evidence: `libs/domain/src/garages/verification.service.ts:36-41,65-71`; `libs/domain/src/garages/garages.module.ts:27-55`; `libs/domain/src/auth/actor.guard.ts:38-39,62-77,108-121`; `libs/domain/src/auth/policy.ts:42-52`; `libs/domain/src/auth/capabilities.ts:43-51`; `libs/contracts/src/problem.ts:40`; `libs/domain/src/notifications/notifications.controller.ts:8-23`.

FR-003 is proven by a test that overrides `MAINTENANCE` with `{ on: async () => true }` (as `sign-in.api.integration.spec.ts:45-46` does), signs the admin in and reads the overview: 200.

- Evidence: `libs/domain/src/auth/actor.guard.ts:62-77`; `libs/domain/src/auth/maintenance.ts:1-10`; `libs/domain/src/auth/auth.module.ts:90`; `libs/domain/src/auth/sign-in.api.integration.spec.ts:45-46`.

## R3. The 404 test walks every `admin/*` route of the OpenAPI document

- Decision: `apps/api/src/admin-routes.integration.spec.ts` boots the API as `public-routes.integration.spec.ts` does (`apiBoot()`, routes from `openApiDocument(app).paths`, `{id}` replaced by a fixed uuid, `public-routes.integration.spec.ts:44-50`), keeps the paths under `/api/v1/admin/`, asserts the list holds at least the four routes known today (`admin/overview`, `admin/live/test`, `admin/notifications/test`, `admin/news`), creates one account per non-admin role through `AccountsService.createAccount` (no garage membership is needed: a `garage` or `receptionist` actor without one has `garageId: null`, and `requireCapability` refuses `admin.*` before the garage check, `policy.ts:45-52`) and expects `404` with `code: 'not_found'` from every route for every role, signed as `live.api.integration.spec.ts:89-90` signs. Signed out: the existing `public-routes` spec already proves 401 `sign_in_required` for every non-public route, the new one included.
- Rationale: FR-002 asks for "every `admin/*` route the API serves": reading the OpenAPI document makes a route that forgets `@Requires` fail the test, which a hand-kept list would not. ST-164 adds its own guard test on data-changing routes later (context.md Constraints).
- Alternatives: one test per route (misses the next route); a Jest `each` over a hand list (same).
- Evidence: `apps/api/src/public-routes.integration.spec.ts:1-129`; `libs/domain/src/events/live.api.integration.spec.ts:79-90,314-337`; `libs/domain/src/auth/policy.ts:45-52`.

## R4. The release mark is one optional field, read by the menu, the bar and the routes

- Decision: `DashboardView` gains `unreleased?: true` (one line on each of the four hidden views: `users`, `reviews`, `catalogue`, `assistant`); `allowedViews` filters it out beside the capability (`views.ts:165-171`), so the side menu (`frame.ts:107-116`, `entries` at `:182-184`) and the tab bar (`frame.ts:146`, `tab-bar.ts:53-64`) hide it; `dashboardRoutes` leaves an unreleased view out of its routes (`views.ts:185-197`), so its address falls through `{ path: '**', redirectTo: '' }` (`views.ts:198`) to "Panou", for every role the area admits (the area guard has already sent the others to their landing, `area.guard.ts:19`). The frame's effect at `frame.ts:210-217` already moves a person off a view that left `entries()`. "Asistent AI" is a new view `{ capability: 'admin.settings', label: 'shell.frame.nav.admin.assistant', path: 'assistant', tab: 'shell.frame.tab.assistant', unreleased: true }` between `catalogue` and `settings`; the story that releases a view deletes its line.
- Rationale: FR-007 wants one mark per view in the one list; `unreleased?: true` changes four lines, not every view of every dashboard, and the default (absent = released) keeps the driver and garage lists untouched. No flag mechanism exists in the repo (spec Assumptions), and an environment variable or stored switch would be a knob nobody reads (Principle I).
- Alternatives: `released: boolean` on every view (26 lines for the same rule); a separate `RELEASED` set keyed by path (a second list beside "the one list").
- Evidence: `apps/web/src/app/dashboard/views.ts:12-22,35-73,165-199`; `apps/web/src/app/dashboard/frame.ts:107-116,146,182-184,201-217`; `apps/web/src/app/dashboard/area.guard.ts:7-20`.

## R5. The counter is read through `liveResource`, with two small additions

- Decision: a component-level `AdminOverview` store (`apps/web/src/app/dashboard/admin-overview.ts`, `providers: [AdminOverview]` on `Frame`, injected only when the frame's area is `admin`) calls `liveResource(() => api.adminOverviewControllerOverview(), ['verification.submitted', 'verification.decided', 'verification.reopened'])`. `liveResource` (`live.ts:359-429`) already debounces a burst into one re-read (`debounceTime(300)`, `:412`), re-reads on `resync` (`:416-418`), reads once at a time (`:396-404`) and retries a failed read after 60 s (`:356,383`). Two additions, both in `live.ts`: the `id` argument becomes optional (no id: every event of those kinds; the overview is about no one object, FR-012's "matched by event kind"); and a `failed: Signal<boolean>` is exposed, true from a failed read (first or background, not a 404) until the next success. The store exposes `loading = resource.isLoading` (true only during the first read, `:374`) and `garagesWaiting = computed(() => resource.failed() ? undefined : resource.value()?.garagesWaiting)`: `undefined` hides the counter and the count (FR-011), the skeleton shows while `loading()`.
- Rationale: FR-012 names the dashboards' shared re-read; `liveResource` is it, and no caller uses it yet (`grep liveResource apps/web/src` finds `live.ts` and its specs only), so the two additions change no screen. Keeping the last value on a failed re-read (`:376-384`, "keeps the data") is the right default for a page and the wrong one for a count (clarify Q1): a signal that says the last read failed lets the admin frame hide the number while the page helper keeps its default.
- Alternatives: a store of its own on `live.events` with `filter` and `debounceTime` (the same 20 lines a second time); `BellStore`'s poll-and-keep shape (`bell.ts:59-73` keeps a failed count, FR-011 forbids it); `httpResource` (no live re-read).
- Evidence: `apps/web/src/app/dashboard/live.ts:141-150,340-429`; `apps/web/src/app/dashboard/bell.ts:28-73`; `apps/web/src/app/dashboard/frame.ts:220-247`.

## R6. The header line, the label, the counter chip and the tab counter live in the frame and the bar

- Decision: `Frame` renders, for the admin area only, a subtitle under the `h1`: an eyebrow `<span>` with the area tag (`shell.frame.area.admin`, now "Administrator" in both languages, upper-cased by CSS `text-transform: uppercase`) and the line `<p>`: `shell.frame.admin.city` ("MotorFix · București" / "MotorFix · Bucharest") joined with ` · ` and the count text; the count text is `shell.frame.admin.none` at 0, `shell.frame.admin.waiting` with `{ count }` above 0 (a plural group: Romanian `one`/`few`/`other`, English `one`/`other`, the forms FR-008 lists), an inline skeleton box while `loading()`, and nothing when `garagesWaiting()` is `undefined`. The count span carries `[mfLiveChange]` (`live-in-place.ts:234-270`) so a live change highlights. The menu entry whose view has `counter: 'garagesWaiting'` (one new optional field on `DashboardView`, set on `garages`) shows a chip with the number and gets `aria-label` = `shell.frame.counter` ("{label}, {n} în așteptare" / "{label}, {n} waiting") when the number is above 0; `DashboardTabBar` gains an input `counts` (`Partial<Record<string, number>>`) and does the same on its tab. The frame's `header` keeps its flex layout (`frame.ts:88-89`); the subtitle wraps (`overflow-wrap: anywhere`, no `white-space: nowrap`) so 320 px never scrolls sideways; every new text uses `var(--mf-size-label)` (12 px, `cockpit.css:28`) or larger.
- Rationale: the frame already owns the header, the menu and the bar for all three areas; an admin-only block in it is smaller than a second header component and keeps one place for the layout. The texts go in the `shell` catalogue: the frame's keys are there, and Romanian shell texts are bundled so the server and the first browser render agree (`files.ts:11-15`); the `admin` area file is empty (`admin/ro.json` is `{}`) and loads asynchronously, which would flash the keys. `I18n.t` selects the plural category from `count` (`i18n.ts:91-103`, `Intl.PluralRules`), and `check.ts:31-40` fails a plural group missing a category; Romanian's rules make 0 `few` and 20+ `other` (`new Intl.PluralRules('ro').select(0) === 'few'`, checked with Node 24), so the zero form is a key of its own chosen in code, and the `other` form carries "de". A param named `count` always selects a category, so the non-plural `shell.frame.counter` key takes `n`. U+2011 in "Service‑uri" (`check.ts:21` refuses a breaking hyphen between letters).
- Alternatives: a `mf-admin-header` component (a second header to keep in step with the frame's); the texts in `libs/i18n/src/admin` (asynchronous, hydration mismatch); a `bell`-style `9+` cap (a queue of 12 must read 12). The chip caps at `99+` above 99 (FR-010, from the checklist), the full count staying in the accessible name: a queue below 100 reads exact.
- Evidence: `apps/web/src/app/dashboard/frame.ts:88-89,103-149`; `apps/web/src/app/dashboard/tab-bar.ts:26-78`; `apps/web/src/app/dashboard/live-in-place.ts:234-270`; `libs/i18n/src/i18n.ts:45-55,91-103`; `libs/i18n/src/files.ts:11-15,18-21`; `libs/i18n/src/check.ts:21,31-40`; `libs/i18n/src/shell/ro.json` (`frame.area.admin` is "Admin" today); `libs/ui-cockpit/src/styles/cockpit.css:28-30`; `apps/web/src/app/dashboard/bell.ts:217-232,240-249`.

## R7. The seed adds two waiting files with one idempotent statement each

- Decision: `seed()` (`seed.ts:177-186`) gains, after the garages, one `INSERT INTO verification_file (id, garage_id, status) SELECT gen_random_uuid(), g.id, $2::verification_file_status FROM garage g WHERE g.slug = $1 AND NOT EXISTS (SELECT 1 FROM verification_file f WHERE f.garage_id = g.id)` per `['service-dobre', 'submitted']` and `['atelier-dinamo', 'in_review']`; `atelier-test` gets none. A second run inserts nothing (the `NOT EXISTS`); the partial unique index `verification_file_one_live` (`migrations/20261007120000_verification_file/migration.sql:40`) would refuse a duplicate anyway. The garages stay `draft` (the seed inserts no status, `seed.ts:179-183`); `in_review` without `opened_by` is a valid row (every `*_by` column is nullable, `garages.prisma:130-135`).
- Rationale: the seed imports nothing from the workspace and speaks SQL (`seed.ts:1-5,178-183`); the file's columns and the enum type's name come from the migration. FR-013's "a second run changes nothing" extends 082-FR-023's rule to the files.
- Alternatives: run `VerificationService.submit` from the seed (imports the workspace, which the seed must not); `ON CONFLICT` (no unique on `garage_id` alone).
- Evidence: `libs/domain/src/seed.ts:1-5,37-41,177-186`; `libs/domain/prisma/schema/garages.prisma:126-146`; `libs/domain/prisma/migrations/20261007120000_verification_file/migration.sql:40`; `libs/domain/src/seed.integration.spec.ts:1-45`.
